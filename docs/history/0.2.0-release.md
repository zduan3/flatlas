# File Atlas 0.2.0 发布记录

> 状态：发布记录。Windows 原生与 WSL 全量验收已记录；机械硬盘基线安排在发布后采集。

File Atlas 起步于个人用 AI 辅助开发的文件索引项目。2026 年 11 月下旬的两次大型清理是它的首次实际应用。两次实践把 0.2.0 的重点定在一条可重复的工作流上：用持久索引盘点占用、筛出清理候选，在外部核对并删除后同步索引，再用同样的口径复查。

## 盘点可重建目录，按清单同步索引

在 Lustre 的百万级索引上，需要按项目汇总字节数和条目数，找出最外层的可重建目录，并估算将这些候选一起删除能腾出多少空间。旧脚本为每个目录反复启动进程、打开 4.6 GB 的索引，生成一份概览耗时约 8.6 分钟。0.2.0 的 `find --format jsonl` 让脚本可以用两次查询分别取得概览和候选，再在本地分组。需要按 hardlink 计量合删可释放空间时，用 `du --files0-from -c --freed` 汇总。用新接口重建的报告与旧报告逐字节一致。 [机器输出约定](../design/queries.md#机器输出)

外部按核对后的清单删除后，可以用同一份清单调用 `rm --files0-from` 移除索引子树。批量同步 2.97 万个目录、122 万行，用时 36 秒；删后项目汇总与按删除前数据推算的结果一致。这次实践推动 0.2.0 固定机器输出的字段与路径约定，并把候选查询、批量空间汇总和索引同步连成脚本流程。 [批量同步实测](../design/queries.md#rm-path--rm---files0-from-file) · [操作配方](../../README.md#脚本与自动化)

## 清理 inode 配额，重扫确认删除

另一次清理的瓶颈是 inode 配额。约 95% 的条目来自同一份源码树的约 200 份副本，每份包含约 1.4 万至 14 万个文件。构建快照和测试运行留下的源码常用 `src`、`source` 这类通用目录名。按条目数排行能定位压力集中的目录，按常见缓存目录名筛选则容易漏掉整树副本。 [Backlog](../plan/backlog.md)

清理后在 Lustre 上重扫原有 391 万行的子树，确认外部已删除约 368 万个路径。重扫共耗时 688 秒，其中 523 秒花在确认删除和写入 tombstone。留下的 tombstone 占该子树索引行数约 94%。0.2.0 据此记录了两种同步方式的取舍：清单已知时按清单移除索引子树，需要从现场确认缺失时重扫仍存在的父目录。 [扫描实测](../design/scanning.md#元数据成本) · [索引保留策略](../plan/decisions.md#索引与历史) · [同步方式](../../README.md#外部删除与索引)

## 版本范围与后续

0.2.0 固定供脚本调用的查询和机器输出约定，并提供批量索引同步。多次查询复用同一索引的 Python API、批量浅扫描和确认删除计数进入 0.2.1；定向清理 tombstone 和重复目录树候选继续留在后续规划中。 [路线图](../plan/roadmap.md) · [Backlog](../plan/backlog.md)

## 发布验收

2026 年 11 月 25 日验收提交 `c4ec106094fa19fdbc8a2e8666b34dd599874230`。Windows 原生和 Ubuntu / WSL2 的 Ruff、pytest、Pyright 和差异检查均通过。Windows 的 pytest 为 303 通过、52 跳过，涉及 symlink 创建和 Linux 或 POSIX 特性。WSL 为 350 通过、5 跳过，均为 Windows 原生 API 用例。 [验收明细](verification-log.md#020-发布验收2026-11-25)

## 发布后性能基线

两次实际清理均未涉及机械硬盘。0.2.0 发布后，待具备 Windows 机械硬盘环境时检出 `v0.2.0`，记录已有索引的刷新、大子树查询的首次与重复运行，以及全量扫描分阶段耗时和索引体积。0.2.2 在同一块盘与同一语料上复测，采集结果记入 [验证记录](verification-log.md)。
